Introducción a la Actividad 1.4.2
El Desafío de la "Triple Restricción": Calidad, Seguridad y Cumplimiento
Contexto: Más allá de "que funcione"
Durante décadas, el desarrollo de software se centró casi exclusivamente en una pregunta: ¿El sistema hace lo que debe hacer? Si la respuesta era "sí", el software se lanzaba. Hoy, esa mentalidad es una receta para el desastre.
En el entorno digital actual, un software funcional pero inseguro es una puerta abierta a los hackers. Un software seguro pero que viola las leyes de privacidad (como GDPR) puede llevar a una empresa a la quiebra por multas millonarias. Y un software legal y seguro, pero imposible de usar, fracasará en el mercado.
Los Tres Pilares de la Confianza Digital
En esta actividad, dejarás de ver las pruebas como una fase final aislada y adoptarás el rol de un Arquitecto de Pruebas Integrales. Trabajarás en la intersección de tres mundos críticos:
Calidad (QA): ¿El producto satisface las necesidades del usuario sin errores? (Rendimiento, Usabilidad, Funcionalidad).
Seguridad (Security): ¿El producto resiste ataques y protege sus activos? (Confidencialidad, Integridad, Disponibilidad).
Cumplimiento (Compliance/Gov): ¿El producto respeta las reglas del juego legales y normativas? (Auditoría, Privacidad, Estándares).
¿Por qué es importante esta actividad?
El mercado laboral actual busca perfiles DevSecOps. Las empresas ya no contratan tres equipos separados para probar esto al final del proyecto; necesitan profesionales capaces de diseñar una estrategia unificada desde el primer día (Shift-Left Testing).
Al diseñar este Plan de Pruebas de Calidad, Seguridad y Cumplimiento, no solo estarás escribiendo un documento; estarás simulando la creación de la red de seguridad que protege a una organización moderna. Aprenderás a priorizar riesgos, a seleccionar las herramientas correctas y a garantizar que el software que entregas sea robusto, legal y confiable.

FICHA DE CASO DE ESTUDIO: PROYECTO "MEDISECURE"
Cliente: Red de Clínicas "Salud Global"
Proyecto: Plataforma MediSecure (Versión 2.0)
Contexto: La clínica está migrando de archivos en papel a una solución digital completa.
1. Descripción del Sistema
MediSecure es una plataforma web y móvil diseñada para la gestión integral de historiales clínicos. Su objetivo es permitir que médicos, enfermeros y administrativos accedan a la información del paciente en tiempo real, mientras los pacientes pueden visualizar sus propios diagnósticos y recetas desde una App móvil.
El sistema maneja información altamente sensible (Datos de Salud - PHI y Datos Personales - PII), por lo que la seguridad no es negociable.
2. Arquitectura Técnica
Frontend: Aplicación Web (React.js) para personal médico y App Móvil (React Native) para pacientes.
Backend: Microservicios en Node.js y Python expuestos vía API REST.
Base de Datos: PostgreSQL (para datos relacionales) y MongoDB (para documentos médicos no estructurados).
Infraestructura: Alojado en la nube (AWS), utilizando contenedores Docker y orquestación con Kubernetes.
Integraciones: Pasarela de pagos externa (Stripe) para el cobro de consultas y servicios.
3. Requerimientos Funcionales (Para Estrategia QA)
El plan de pruebas debe cubrir los siguientes flujos críticos:
Gestión de Citas: El paciente debe poder agendar, reagendar y cancelar citas desde la App.
Historial Clínico: El médico debe poder crear y editar diagnósticos. Restricción: Un médico no puede editar un historial cerrado hace más de 48 horas sin permiso de un supervisor.
Recetas Electrónicas: Generación de PDF de recetas y envío automático al correo del paciente.
Rendimiento: El sistema debe soportar 5,000 usuarios concurrentes (lunes por la mañana) sin que el tiempo de carga supere los 2 segundos.
4. Requerimientos de Seguridad (Para Estrategia Sec/DevSecOps)
El equipo de seguridad ha levantado las siguientes alertas que deben probarse:
Autenticación: Todo acceso externo debe requerir Autenticación de Doble Factor (2FA/MFA).
Control de Acceso (RBAC):
Administrativos: Solo ven datos de contacto y facturación.
Enfermeros: Ven signos vitales y medicación, pero no diagnósticos psiquiátricos.
Médicos: Acceso completo a historias clínicas de sus pacientes asignados.
Vulnerabilidades Web: El historial de versiones anteriores mostró problemas de Inyección SQL y Cross-Site Scripting (XSS). El nuevo plan debe garantizar que esto no ocurra.
5. Requerimientos de Cumplimiento (Para Estrategia Gov)
El sistema opera bajo regulaciones estrictas:
HIPAA (Ley de Portabilidad y Responsabilidad del Seguro Médico): Exige que todos los datos de salud estén encriptados tanto en tránsito (HTTPS) como en reposo (Base de datos encriptada).
GDPR (Reglamento General de Protección de Datos): El paciente tiene derecho a descargar todos sus datos en un formato legible (XML/JSON) y a solicitar la eliminación de su cuenta ("Derecho al Olvido"), excepto los datos médicos que la ley obligue a conservar.
Auditoría: Cada vez que alguien visualiza un registro médico, el sistema debe guardar un log inalterable con: ID de usuario, Fecha, Hora, IP y Registro accedido.
6. Restricciones del Proyecto (Para Matriz de Riesgos)
Tiempo: El lanzamiento es en 4 semanas. No hay tiempo para probar manualmente todo el sistema.
Presupuesto: Limitado para herramientas de pago; se prefieren herramientas Open Source (como JMeter, OWASP ZAP).
Entorno: El entorno de "Staging" (Pruebas) tiene datos anonimizados, pero a veces se desincroniza del entorno de Producción.
